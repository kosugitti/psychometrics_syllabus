# Bandmaster -- マルチエージェント・オーケストレーション・システム

## 1. 設計思想

### 1.1 基本コンセプト

オーケストラの比喩に基づくマルチエージェントシステム。
指揮者(ユーザー)の意図をバンドマスター(取次役)が受け取り，各奏者(ワーカーエージェント)に振り分ける。

- **ユーザー** = 指揮者。作業の方向性と最終判断を担う
- **バンマス** = バンドマスター(取次役)。指揮者の意図を奏者に伝達し，奏者の報告を指揮者に届ける
- **ワーカーエージェント** = 奏者。各自の専門領域で実作業を行う
- **ウォッチャー** = ステージマネージャー。奏者の状態を監視し，報告をバンマスに中継する

### 1.2 なぜ取次役が必要か

Claude Code の単体エージェントでも多くの作業は可能だが，以下の理由で取次役を介した分業が有効である：

1. **専門性の分離**: 校閲・ビルド・研究課題作成など，異なるスキルセットを持つエージェントを並行稼働できる
2. **コンテキストの保全**: 各エージェントが自分の担当領域のコンテキストだけを保持するため，長い会話でのコンテキスト消費を抑制
3. **ユーザーの認知負荷軽減**: ユーザーは1つの窓口(バンマス)に話しかけるだけでよい
4. **安全弁**: バンマスが振り分け判断を行うことで，誤った操作の防止層になる

### 1.3 設計原則: ファイルが通信路

**Claude Code の CLI は他の CLI の画面に直接出力できない。** これがマルチエージェント構築の最大の制約である。

この制約を踏まえ，本システムは以下の原則に基づく：

- **ファイルが内容を運ぶ**: タスク指示も報告もすべてテキストファイル(Markdown)で受け渡す。長文でも構造化データでも壊れない
- **tmux は最小限のトリガーだけ**: tmux send-keys で送るのは `"check"` の1単語のみ。長いメッセージを send-keys で送ることはしない
- **ウォッチャーがイベント駆動を担う**: ファイルの変更を検知し，該当エージェントやバンマスにトリガーを送る独立プロセス

### 1.4 権限モデル

```
ユーザー（全権限）
  |
  v
バンマス（--dangerously-skip-permissions）
  - queue/agentN/task.md の書き込み（タスク振り分け）
  - queue/agentN/report.md の読み取り（報告確認）
  - ユーザーへの報告
  - 自分では作業コンテンツ（tex, R等）を編集しない
  |
  v
ワーカーエージェント（--dangerously-skip-permissions）
  - 作業コンテンツの編集（tex, R等）→ システムプロンプトで承認フロー制御
  - queue/agentN/report.md への書き込み
  - queue/agentN/task.md の読み取り
  - 安全弁: Git ブランチによる変更の隔離と復元
```

**なぜ全エージェントが skip-permissions なのか:**

Claude Code のパス単位の権限チェックを tmux 経由で事前承認する仕組みは，タイミング問題により信頼性が確保できなかった（詳細は設計変遷ログ v3.1 参照）。代わりに以下の二重の安全弁で制御する:

1. **システムプロンプト**: エージェントは report.md で提案 → ユーザー承認 → 実行のフローに従う
2. **Git ブランチ**: Agent1/Agent2 は専用ブランチで作業。万一の誤編集も `git checkout` で即復元可能

### 1.5 Git ブランチモデル

```
main (安定版)
  |
  +-- agent1/xxx  ← Agent1(クラリネット) の作業ブランチ
  |
  +-- agent2/xxx  ← Agent2(オーボエ) の作業ブランチ
  |
  (Agent3 がコンパイル前にマージ → コンフリクトあれば報告)
```

- **Agent1/Agent2**: tex 編集前に `agent1/xxx` `agent2/xxx` ブランチを作成。main では編集しない
- **Agent3**: コンパイル前に agent1/ agent2/ ブランチを main にマージ。コンフリクト時は abort して報告
- **ユーザー**: コンフリクト解決の最終判断。マージ結果の確認

## 2. アーキテクチャ

### 2.1 システム構成

```
iTerm2 ウィンドウ1 (リンクドセッション: mywork-agents)
┌──────────────────────────────────────┐
│ tmux window 0 "agents"               │
│ ┌──────────┬──────────┬──────────┐  │
│ │ pane 0   │ pane 2   │ pane 3   │  │
│ │ Agent1   │ Agent2   │ Agent3   │  │
│ │ クラリネット    │ オーボエ    │ファゴット│  │
│ │ 研究課題  │ 校閲     │ ビルド    │  │
│ ├──────────┴──────────┴──────────┤  │
│ │ pane 1: Watcher/Dashboard      │  │
│ │ [!] オーボエ: 承認待ち 16:05     │  │
│ │ [>] クラリネット: 作業中             │  │
│ └────────────────────────────────┘  │
└──────────────────────────────────────┘

iTerm2 ウィンドウ2 (リンクドセッション: mywork-bm)
┌──────────────────────────────────────┐
│ tmux window 1 "bandmaster"           │
│ ┌────────────────────────────────┐  │
│ │ バンマス CLI                    │  │
│ │ > オーボエから報告が参りました     │  │
│ │   承認しますか?                 │  │
│ └────────────────────────────────┘  │
└──────────────────────────────────────┘
```

**リンクドセッション**: `mywork`(本体), `mywork-agents`, `mywork-bm` の3つのセッションが同じウィンドウ群を共有するが，どのウィンドウを表示するかは独立。iTerm2 の2つのウィンドウが互いに干渉しない。

### 2.2 通信プロトコル

#### ファイルキュー構造

```
agents/queue/
├── agent1/
│   ├── task.md      ← バンマスが書く（指示）
│   └── report.md    ← エージェントが書く（報告）
├── agent2/
│   ├── task.md
│   └── report.md
└── agent3/
    ├── task.md
    └── report.md
```

#### バンマス → エージェント（指示）

```
バンマス --[Bash: cat >]--> queue/agentN/task.md
                              ↓ (mtime変化)
watcher.sh --[tmux send-keys "check"]--> エージェントのpane
                                           ↓
エージェント --[Read]--> queue/agentN/task.md を読んで作業開始
```

#### エージェント → バンマス（報告）

```
エージェント --[Bash: cat >]--> queue/agentN/report.md
                                  ↓ (mtime変化)
watcher.sh --[tmux send-keys "check"]--> バンマスのpane
                                           ↓
バンマス --[Read]--> queue/agentN/report.md を読んでユーザーに報告
```

#### task.md の形式

```markdown
# Task
- status: pending | approved | none
- timestamp: YYYY-MM-DD HH:MM:SS
- type: タスク種別

## Instructions
具体的な作業指示
```

#### report.md の形式

```markdown
# Report
- status: needs_approval | completed | error | idle
- summary: 作業結果の要約(1行)
- timestamp: YYYY-MM-DD HH:MM:SS

## Details
詳細な作業結果・提案内容・エラー情報
```

### 2.3 タスクライフサイクル

```
[ユーザー指示]
    |
    v
[バンマスが振り分け判断]
    |
    v
[task.md 作成 (status: pending)]
    |
    v  (watcher.sh が mtime 変化を検知)
[エージェントに "check" トリガー]
    |
    v
[エージェントが task.md を読んで作業開始]
    |
    v
[作業完了 → report.md 作成 (status: needs_approval / completed)]
    |
    v  (watcher.sh が mtime 変化を検知)
[バンマスに "check" トリガー]
    |
    v
[バンマスが report.md を読んでユーザーに報告]
    |
    v  (needs_approval の場合)
[ユーザーが承認 → バンマスが task.md 更新 (status: approved)]
    |
    v  (watcher.sh が再検知 → エージェントに "check")
[エージェントが承認を確認 → 修正実行 → report.md 更新 (status: completed)]
```

### 2.4 ファイル構成

```
agents/
├── ARCHITECTURE.md       # 本ファイル（設計文書）
├── bandmaster.md         # バンマスの system prompt
├── agent1.md             # Agent1(クラリネット) の system prompt
├── agent2.md             # Agent2(オーボエ) の system prompt
├── agent3.md             # Agent3(ファゴット) の system prompt
├── watcher.sh            # ファイル監視 + ダッシュボード + トリガー送信
├── launch.sh             # システム一括起動スクリプト
├── stop.sh               # システム停止スクリプト
└── queue/                # ファイルキュー（通信路）
    ├── agent1/
    │   ├── task.md       # バンマス → Agent1 への指示
    │   └── report.md     # Agent1 → バンマス への報告
    ├── agent2/
    │   ├── task.md
    │   └── report.md
    └── agent3/
        ├── task.md
        └── report.md
```

**旧ファイル（非推奨・削除可能）：**

```
agents/
├── bandmaster.sh         # 旧: バンマス単体起動（launch.sh に統合済み）
├── send_task.sh          # 旧: 手動タスク送信（queue方式に移行済み）
└── tasks/                # 旧: YAMLタスクファイル（queue方式に移行済み）
    ├── agent1.yaml
    ├── agent2.yaml
    └── agent3.yaml
```

## 3. 使い方

### 3.1 起動

```bash
bash agents/launch.sh
```

実行すると以下が自動で行われる：

1. `agents/queue/` ディレクトリと初期ファイルの作成
2. tmux セッション `mywork` の作成（2ウィンドウ: agents + bandmaster）
3. Agent 3体の起動（tmux window 0, pane 0/2/3）
4. watcher.sh の起動（tmux window 0, pane 1）
5. バンマスの起動（tmux window 1）
6. 各エージェントの Bash 権限の事前承認
7. iTerm2 の起動とウィンドウ2つの表示

起動完了後の画面：

- **iTerm2 ウィンドウ1**: エージェント3体 + ダッシュボード（仕事やってる感）
- **iTerm2 ウィンドウ2**: バンマス（ここに指示を打つ）

### 3.2 操作

**指示を出す：** バンマスのウィンドウで自然言語で指示する。

```
> 第7章の校閲をお願い
  → バンマスが Agent2(オーボエ) に振り分け

> 第8章の研究課題を作って
  → バンマスが Agent1(クラリネット) に振り分け

> コンパイルして
  → バンマスが Agent3(ファゴット) に振り分け
```

複数のエージェントへの同時指示も可能。バンマスが順番にタスクファイルを書く。

**報告を受ける：** エージェントが作業を完了（または承認を求める）と，watcher.sh が検知してバンマスに `"check"` トリガーを送る。バンマスが report.md を読んでユーザーに報告する。

**承認する：** バンマスが「承認しますか？」と聞いてきたら，「承認」と返答する。バンマスが task.md を `status: approved` で更新し，エージェントが作業を続行する。

### 3.3 画面切り替え（tmux）

iTerm2 内で tmux のウィンドウを切り替えられる：

- `Ctrl+b, 0` → エージェント画面（仕事やってる感を見る）
- `Ctrl+b, 1` → バンマス画面（指示を出す）

ただしリンクドセッションを使っているため，通常は iTerm2 のウィンドウ切り替え（Cmd+`）で十分。

### 3.4 停止

```bash
# 丁寧に終了（各 Claude Code に /exit → watcher 停止 → セッション削除）
bash agents/stop.sh

# 即座に全部落とす（急ぎの時）
tmux kill-session -t mywork
```

## 5. 技術的な補足

### 5.1 watcher.sh の動作

- 3秒ごとに `agents/queue/*/task.md` と `agents/queue/*/report.md` の mtime（ファイル更新日時）をチェック
- mtime が前回と異なれば「ファイルが変更された」と判定
- 起動時の mtime をベースラインとして記録し，既存ファイルの誤検知を防止
- ダッシュボード表示: 全エージェントの status/summary を一覧表示

### 5.2 権限と安全性

全エージェントが `--dangerously-skip-permissions` で起動される。安全性は以下で担保:

1. **システムプロンプトによる行動制御**: 各エージェントの .md に「報告→承認→実行」フローを明記
2. **Git ブランチによる隔離**: Agent1/Agent2 は専用ブランチで作業。main を直接汚さない
3. **Agent3 によるゲートキーピング**: コンパイル前にマージし，コンフリクトがあれば報告
4. **git による即時復元**: 万一の場合は `git checkout`, `git branch -D` で即座に復元可能

### 5.3 リンクドセッション

tmux の `new-session -t` で作成するリンクドセッションは，親セッションとウィンドウ群を共有しつつ，どのウィンドウを表示するかは独立に制御できる。これにより iTerm2 の2ウィンドウが互いに干渉しない。

```
mywork          ← 本体セッション（エージェント・バンマスが動作）
mywork-agents   ← リンクドセッション（iTerm2 ウィンドウ1が接続）
mywork-bm       ← リンクドセッション（iTerm2 ウィンドウ2が接続）
```

### 5.4 現時点の制約と今後の課題

1. **tmux 依存**: トリガー送信に tmux を使用。他のターミナルマルチプレクサには未対応
2. **ポーリング方式**: 3秒間隔のポーリング。fswatch 等のイベント駆動に改善余地あり
3. **入力衝突**: ユーザーがバンマスに入力中に watcher が "check" を送ると混ざる可能性（実害は軽微）
4. **1エージェント1タスク**: 各エージェントは同時に1タスクのみ処理。キュー機能は未実装
5. **エージェント再起動**: tmux pane 内の Claude Code セッションが切れた場合の復旧手順が未整備

## 6. 設計変遷ログ

### v1 (2026-02-07): 初版 -- tmux send-keys + capture-pane 方式

- バンマスが tmux send-keys で長文メッセージをエージェントに送信
- エージェントが `===TASK_REPORT===` マーカーを画面に出力
- バンマスが tmux capture-pane でポーリングして報告を検知

**問題:** tmux send-keys で C-m が補完メニューに吸われる，capture-pane のパースが不安定，バンマスがバックグラウンド監視の結果を処理するにはユーザー入力が必要（デッドロック）

### v2 (2026-02-07): 改善 -- マーカー + 信号ファイル二重報告

- エージェントが画面マーカーと `/tmp/agentN_signal.txt` の両方に報告
- バンマスの監視をベースラインカウント方式に改善

**問題:** 二重報告の不整合（bandmaster.md は capture-pane のみ監視），根本的なデッドロックは未解決

### v3 (2026-02-07): ファイルキュー + watcher 方式

- **通信をすべてファイルベースに変更**: task.md / report.md によるキュー方式
- **watcher.sh を導入**: ファイル変更を検知し，最小限のトリガー（"check" 1単語）を tmux 経由で送信
- **tmux レイアウトを2ウィンドウ構成に変更**: agents+watcher / bandmaster
- **リンクドセッションを導入**: iTerm2 の2ウィンドウが独立動作
- **stop.sh を追加**: graceful shutdown スクリプト

**解決した問題:** CLI 間の直接通信不能，tmux send-keys の不安定さ，バンマスのデッドロック，capture-pane の脆弱なパース

### v3.1 (2026-02-07): 現行 -- skip-permissions + Git ブランチ方式

- **全エージェントを `--dangerously-skip-permissions` で起動**: tmux 経由の権限事前承認がタイミング問題で不安定だったため廃止
- **Git ブランチモデルを導入**: Agent1/Agent2 は専用ブランチ(`agent1/xxx`, `agent2/xxx`)で作業。main を直接編集しない
- **Agent3 にマージ責務を追加**: コンパイル前に agent1/ agent2/ ブランチを main にマージ。コンフリクト時は abort して報告
- **pane ID (`%N`) によるペイン管理**: tmux の位置ベースインデックス振り直し問題を解決。`.pane_ids` ファイルで ID を永続化
- **起動高速化**: 事前承認ステップ廃止 + ポーリング待機により起動時間を約10秒に短縮
- **`aggressive-resize`**: リンクドセッション間のサイズ連動を防止

**解決した問題:** 権限プロンプトのタイミング問題，ペイン番号のずれ，起動の遅さ，画面サイズの連動

**安全性の担保:** システムプロンプトによる行動制御 + Git ブランチによる変更隔離 + 即時復元可能性
